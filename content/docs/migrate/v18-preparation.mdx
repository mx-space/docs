<Callout type="warn">
v18 尚未发布。本开发分支已移除非加密运行和旧格式写入，启动必须提供显式字段密钥与至少 32 字符的 JWT。本文的 `upgrade:*` 工具尚未发布，已发布的 v17.0.4 不包含它们。最低准备版 tag、SDK、CLI 和主题版本会在实际发布验证后补齐；不要直接在现有镜像上运行不存在的命令。
</Callout>

## 计划改变什么

| 范围 | 当前 v17 | v18 计划 |
| --- | --- | --- |
| 凭据写入 | v17.0.4 可分阶段启用 V2，有临时明文逃生口 | **本开发分支已生效**：显式 hex64 字段密钥、JWT 至少 32 字符、固定 V2；旧关闭配置报错 |
| 普通摘要、精读 GET | 可能隐式生成 | 只读，无结果 `data: null`；生成显式触发 |
| 非流式执行入口 | 旧 GET 可用 | 备份、清缓存、测试邮件与速记表态用 POST；GET SSE 保留 |
| 配置与参数 | 保留旧配置、排序与别名兼容 | 拒绝未知声明字段、数字排序；移除评论列表 `state` 查询别名，更新 body 的 state 仍可用 |
| AI 元数据 | 旧响应字段保留 | 统一 generationMetrics，后续才删除旧列与旧响应字段 |
| SDK | 5.x 兼容版先转换请求 | 协调 SDK 6.x；保留 legacy 入口与 CLI V2 响应适配 |

加密强制已在本分支实现；其余最终破坏仍分阶段推进。当前继续支持旧 GET 和 SDK 5.x 签名，不改变普通 AI GET 的既有行为，不删除物理列。API `/api/v3`、snake_case、成功/错误 envelope 和 SSE 帧协议保持。

## 准备顺序

1. 更早的实例先按历史指南升级到兼容的 v17，保存数据库、文件、原字段密钥、原 JWT 和备份私钥。
2. 取得包含工具的构建，先不要启动业务副本。独立工具读取 `PG_URL` / `PG_CONNECTION_STRING` 或 `PG_*`、字段密钥和 JWT；业务进程用 CLI/YAML 配置时，也要提供等效环境变量。先用 check 诊断现有配置。
3. JWT 不足 32 字符时先执行下方维护轮换。不要直接改环境变量，否则现有 OAuth token 可能无法解密。
4. 删除 `ENCRYPT_ENABLE`、`MX_ENCRYPT_ENABLE` 和 `MX_SECRET_STORAGE_V2`，保存原有效字段密钥与符合要求的 JWT。停止旧副本及后台写入者，再部署本构建到全部副本；新写入自动加密，无需启用开关。确认没有旧格式写入者，再执行准备。
5. 检查、dry-run、正式 prepare，完成后重启业务副本，验证原 API Key、OAuth、配置消费与 AI 指标。

### 启动配置与旧开关

- `MX_ENCRYPT_KEY` 或 `ENCRYPT_KEY` 必须是显式的 64 位十六进制密钥；不再回退到机器 ID，也不再派生短密钥。只有从未加密的新实例才用 `openssl rand -hex 32` 生成首个字段密钥并持久保存。
- `JWT_SECRET`（别名 `JWTSECRET`）至少 32 字符；已有短 JWT 必须先按下方维护流程轮换。
- 旧开关的 `true` 值暂接受并提示删除；`false` 或其他无效值会阻止启动，check 报告 `DEPRECATED_ENCRYPTION_FLAG`。它们不再控制运行模式。
- 配置、Snippet 和 Webhook 固定认证加密，API Key 固定哈希，OAuth 固定加密；历史明文和 ECB 仍可读取并显式迁移。`ENCRYPT_ALGORITHM` 只用于历史读取。
- app 与 mx-migrate 使用相同且持久保存的密钥。字段加密必填不影响 ZIP 备份和历史归档读取；备份加密仍由独立设置控制。

源码工作区中的命令（需要本分支代码和已完成 schema 迁移的数据库）：

```bash
pnpm -C apps/core upgrade:check --json
pnpm -C apps/core upgrade:prepare --all-replicas-v2 --dry-run
pnpm -C apps/core upgrade:prepare --all-replicas-v2
pnpm -C apps/core upgrade:check --json
```

构建产物中使用 `node upgrade.mjs check --json`、`node upgrade.mjs prepare --all-replicas-v2 --dry-run` 和正式 prepare。在包含该入口的镜像中，可使用 `docker compose run --rm --no-deps app node upgrade.mjs check --json` 启动独立检查；数据库需已运行。该进程不启动 HTTP、业务定时任务或 Redis。当前分支的 Compose 会先校验密钥和 JWT 非空；诊断缺失配置时使用源码命令或直接 `docker run`，避免先被 Compose 拦截。

`check` 退出码：`0` 为 ready，`2` 为 needs-action，`1` 为检查失败。它只读，输出计数和路径，不输出秘密。空库可识别为新装，不要求历史准备标记；历史实例须完成实际转换。

`--all-replicas-v2` 是操作者对全部副本状态的明确确认，工具不能自动检查集群。prepare 持有数据库锁，与正常配置 PATCH 串行；按原路径解密，再转换配置、重新加密、哈希旧 API Key、封装 OAuth 并补齐指标。原 API Key 字符串保持有效。dry-run 在事务内演练后回滚，`would-be-ready` 不代表数据库已经准备完成。

只有全部残留检查通过才记录准备标记。损坏密文、未知配置形状、错误字段密钥或 JWT 都会失败并回滚。准备完成后重启副本淘汰旧配置缓存，不清空所有 Redis 状态。旧 `migrate:secrets` 账本不能替代此检查。

如果规范凭据为空，转换会保留已有旧凭据；新旧值都非空且不同时，检查返回 `CONFIG_SECRET_CONFLICT` 与字段路径，准备停止。在后台重新明确填写要保留的规范凭据并保存，再运行检查。旧配置读取继续兼容，但不明确替换凭据的部分保存不能悄悄删除冲突值。

## 维护窗口轮换 JWT

先停止全部业务副本、后台任务和其他写入者。将原 JWT 和至少 32 字符的新 JWT 放在两个仅操作者可读的文件中，不把秘密值放在命令行或聊天记录里：

```bash
pnpm -C apps/core upgrade:rotate-jwt --maintenance-confirmed --old-jwt-file /secure/old-jwt --new-jwt-file /secure/new-jwt
```

构建产物对应 `node upgrade.mjs rotate-jwt` 加同样参数；容器以只读 volume 挂载这两个文件，再传容器内路径。工具只读取文件，不改写秘密文件或业务环境。

事务内用旧 JWT 解开 OAuth，再用新 JWT 重封装；保留 provider token，不联系服务商，不改字段密钥和 API Key。成功会清空登录会话，所有用户须重新登录。之后由操作者将 **全部副本** 配置为同一新 JWT，再启动。失败整批回滚；原 JWT 丢失时不得清空 token 伪装成功，应找回原秘密或重新授权。

历史 Better Auth 裸 hex 密文也会验证与转换。疑似该格式但验证失败的 token 会阻塞操作，需要核对原秘密或重新授权，不会当明文继续。

## 消费者与恢复边界

兼容 SDK 将速记表态改为 POST，并把数值排序转换成 `asc` / `desc`；已有 token 参数转为认证头。Admin 的备份、清缓存与测试邮件提前走 POST。尚未验证的客户端不能宣称兼容 v18。

回退最低版本须是经过实测的准备版，当前发布 tag 尚未确定。回退代码不会回退 schema；回到更老版本必须有旧快照和当时的秘密。

当前恢复工具没有 v18 隔离预检闭环。历史 ZIP 或 v1 加密归档应先在隔离的准备版环境中恢复，用归档当时的字段密钥、JWT、恢复私钥完成 check / prepare，再验证并安排未来 v18 切换；不要把未准备数据直接交给 v18 业务。数据库恢复和文件恢复是两个阶段，保留恢复前快照。
